# QuickNotes Data Model

The backend stores account data and notes in a relational database. IDs are generated by the database; timestamps are stored in UTC.

## Entities and relationships

- **users** stores one account per user, with a unique email and account creation time.
- **notes** stores a user's title and optional body, plus creation and update timestamps.
- **tags** stores a user's reusable labels; tag names are unique within one user's tag collection.
- **note_tags** records which tags are attached to which notes and prevents duplicate note/tag pairs.

A user has zero or many notes, so `users` to `notes` is one-to-many; each note has exactly one owner. A user also has zero or many tags, so `users` to `tags` is one-to-many. Notes and tags are many-to-many: a note can have several tags and a tag can label several notes. `note_tags` is needed as a join table to represent each association and enforce one row per pair. The API must verify that the note and tag belong to the same user before creating that association.

## PostgreSQL schema

```sql
CREATE TABLE users (
  user_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email VARCHAR(254) NOT NULL UNIQUE,
  display_name VARCHAR(100) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE notes (
  note_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users (user_id) ON DELETE CASCADE,
  title VARCHAR(100) NOT NULL CHECK (CHAR_LENGTH(BTRIM(title)) > 0),
  body TEXT NOT NULL DEFAULT '',
  created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE tags (
  tag_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users (user_id) ON DELETE CASCADE,
  name VARCHAR(50) NOT NULL CHECK (CHAR_LENGTH(BTRIM(name)) > 0),
  created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (user_id, name)
);

CREATE TABLE note_tags (
  note_id BIGINT NOT NULL REFERENCES notes (note_id) ON DELETE CASCADE,
  tag_id BIGINT NOT NULL REFERENCES tags (tag_id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (note_id, tag_id)
);
```

The `note_tags` composite primary key is also the uniqueness rule: the same tag cannot be attached to the same note twice. Cascading deletes remove dependent notes or associations when their owning user, note, or tag is deleted.

## Example queries

List the latest notes for a user:

```sql
SELECT note_id, title, body, created_at, updated_at
FROM notes
WHERE user_id = 42
ORDER BY updated_at DESC, note_id DESC
LIMIT 20;
```

Get a note with its tags (a note with no tags is still returned):

```sql
SELECT n.note_id, n.title, n.body, t.tag_id, t.name AS tag_name
FROM notes AS n
LEFT JOIN note_tags AS nt ON nt.note_id = n.note_id
LEFT JOIN tags AS t ON t.tag_id = nt.tag_id
WHERE n.user_id = 42 AND n.note_id = 101
ORDER BY t.name;
```

Count notes per user, including users with no notes:

```sql
SELECT u.user_id, u.display_name, COUNT(n.note_id) AS note_count
FROM users AS u
LEFT JOIN notes AS n ON n.user_id = u.user_id
GROUP BY u.user_id, u.display_name
ORDER BY u.user_id;
```

List tags used on a user's notes:

```sql
SELECT DISTINCT t.tag_id, t.name
FROM tags AS t
JOIN note_tags AS nt ON nt.tag_id = t.tag_id
JOIN notes AS n ON n.note_id = nt.note_id
WHERE n.user_id = 42
ORDER BY t.name;
```

## Index

```sql
CREATE INDEX idx_notes_user_updated_at
  ON notes (user_id, updated_at DESC, note_id DESC);
```

This index supports the common `GET /notes` access pattern by quickly finding one user's newest notes in pagination order without sorting the entire notes table.

## SQL or NoSQL?

I would choose SQL, specifically PostgreSQL, because notes have clear ownership and tags form a many-to-many relationship that benefits from foreign keys and uniqueness constraints. Transactions keep note changes and tag assignments consistent, and relational indexes and queries fit the expected user-scoped feed. A document store could work, but embedding tag data would duplicate it across notes and make shared tag updates and integrity checks harder.
